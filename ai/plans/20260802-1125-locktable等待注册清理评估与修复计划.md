# 等待注册清理实施计划

> **For Codex:** REQUIRED SUB-SKILL: execute this plan task-by-task with test-first checkpoints, detailed pre-commit summaries, and one push after each completed commit.

**Goal:** 修复 [`LockTable`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L48) 的等待注册清理缺陷，补齐异常/早退路径测试，并建立能够判定该类生命周期错误而不过度放大核心隔离模型的模型测试层。

**Architecture:** 生产修复保持最小：五个 acquire 入口用外层 finally 清理事务到 anchor 的注册，用内层 finally 清理真实 waiter 注册。隔离安全模型 [`L1`](../../research/plan.md#l1单层-sx-strict-2pl) 不直接扩张为完整 Java 控制流；新增正交的 wait-lifecycle micro-model 和 quiescent white-box probe，把 cleanup/progress obligation 与 owner compatibility 分开检查，再用少量跨层 canonical traces 连接两者。

**Tech Stack:** Java 8-compatible source、JUnit 4、TLA+ Tools 1.7.4、Python 3.10+ 标准库、Maven/JDK 17、Git isolated worktrees。

## 1. 审计结论

### 1.1 判定

| 问题 | 结论 | 证据强度 |
| --- | --- | --- |
| 是否是正确性问题 | **是**。acquire 调用在返回或抛出后仍可能保留“事务正在等待”的内部状态，违反 quiescent cleanup contract。 | High |
| 是否是 bug | **是，已确认**。上游 [PR #95](https://github.com/vanilladb/vanillacore/pull/95) 明确指出重入后 [`txWaitMap`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L105) 未清理，并提交了相同方向的 finally 修复；本项目已有确定性差分见证。 | High |
| 是否直接破坏 isolation safety | **尚未发现，也不能据现有证据声称会直接破坏。** 两个残留结构不参与锁兼容判定或 owner 授予；已观察后果是错误内部状态、错误/多余通知、内存与 liveness 风险。 | Medium |
| 是否完全不影响 isolation | **不能下此结论。** 当前没有覆盖中断、timeout、deadlock-abort 与三种 isolation manager 的端到端 A/B histories；只能写成“bounded scope 内未建立 isolation violation”。 | Medium |

因此，缺陷分类应为 **confirmed internal correctness bug / cleanup and progress risk / isolation-safety impact not established**，而不是“仅性能问题”或“已证明 isolation bug”。

### 1.2 两个需要分开的清理缺陷

1. **外层事务等待映射。** 五个入口 [`sLock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L177)、[`xLock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L222)、[`sixLock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L267)、[`isLock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L311) 与 [`ixLock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L353) 都先写 [`txWaitMap`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L181)，但只在正常落出 synchronized block 后删除。重入 return、interrupt、timeout 和 [`avoidDeadlock`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L124) 抛出的 abort 都会绕过该删除。
2. **内层资源 waiter 集合。** [`requestSet.add`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L192) 与 [`requestSet.remove`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L197) 没有 finally 保护。可以确定 interrupt 在 [`Object.wait`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L196) 处抛出时会同时遗留 requestSet；普通 timeout 会先从 wait 返回并执行 remove，deadlock abort 通常在 add 前或一次 wake/remove 后发生，所以引用描述若把 requestSet 的所有 timeout/deadlock 路径都称为泄漏，范围过宽。外层 txWaitMap 对这些路径的泄漏判断仍然成立。

[`requestSet`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L70) 当前只阻止空 locker entry 被删除，不参与 [`sLockable`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L652) 或 [`xLockable`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L657)；[`txWaitMap`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L105) 只被 notifier 用于定位 monitor。因此残留首先破坏 cleanup、bounded resource 和通知精确性，而不是放宽冲突矩阵。

## 3. 模型未捕获的根本原因

### 3.1 不只是“粒度太粗”

根因由四部分共同构成：

1. **状态抽象缺口：** [`VC_L1_SX`](../../tla/l1/VC_L1_SX.tla#L19) 的 pending 状态表达逻辑请求，不表达 Java notifier registry、anchor identity 或 requestSet membership。
2. **动作域缺口：** mapping 明确把 repeated S request 视为当前 action set 之外的幂等实现行为；恰好遗漏重入 early-return 路径。
3. **观测缺口：** [`WAIT_BEGIN`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/trace/LockTraceEventType.java#L5) 只证明 add 后即将 wait，没有 WAIT_END、LOCK_RETURN、INTERRUPT 或 ABORT 事件；[`PendingWellFormed`](../../tla/l1/mapping-v0.1.json#L238) 的 source mapping 不能替代真实 snapshot。
4. **oracle 时点错误：** Week 2 在 transaction end 后看终态；[`releaseAll`](../../src/main/java/org/vanilladb/core/storage/tx/concurrency/LockTable.java#L465) 清除了 txWaitMap，使“方法返回后的错误中间状态”被后续清理掩盖。

因此，单纯在现有 L1 再加一个 TerminalClean invariant 仍抓不到该 bug；必须增加 **quiescent call-return/throw checkpoint + implementation-state observation**。

### 3.2 如何权衡粒度与复杂度

不把全部 Java map、1009 个 anchor、线程与时钟直接乘入核心锁模型。采用以下 inclusion rule：某字段满足任一条件才进入模型或 observer：

- 会改变 lock safety、abort/notify progress 或 terminal/quiescent cleanup；
- 是模型动作可执行性的必要证据；
- 对应已注册 fault hypothesis，且简单 history oracle 不可见。

按此规则，txWaitMap 与 requestSet **应被观测**，但只需抽象为 transaction→resource-or-none 和 transaction/resource→boolean；无需建模 Java HashMap bucket、anchor 数组索引或 notifier thread 实现。

复杂度控制采用分解而不是删语义：

1. 核心 [`L1`](../../research/plan.md#l1单层-sx-strict-2pl) 继续负责 ownership、compatibility 与 strict release；
2. 新建独立 wait-lifecycle micro-model，负责 register、reentrant return、wait、wake、grant、timeout、interrupt、deadlock abort 和 cleanup；
3. 只用少量 canonical traces 做 assume-guarantee 连接，不对两个状态空间做无条件笛卡尔积；
4. 主计划本就把 waiter/request set、anchor/notification、timeout 和 abort 放在 [`L3`](../../research/plan.md#l3等待age-based-aborttimeout-与恢复)，micro-model 是 L3 前置组件，不冒充完整 L3。

### 3.3 能否只以“最终 isolation levels 保障”为准则

**不能作为唯一准则，可以作为最高优先级准则之一。** 只看已提交事务的最终 isolation history 会漏掉：永久等待、错误 victim 通知、abort 后残留、内存无界增长、recovery 前释放、测试间污染和诊断不可判定；这些都是数据库正确性或可用性问题。

建议采用四层 contract：

1. **Safety:** declared isolation、atomicity、owner compatibility；
2. **Progress:** waiter 最终 grant/abort、正确 victim 被唤醒、无永久阻塞；
3. **Lifecycle hygiene:** 方法 quiescent point 与 transaction terminal point 无幽灵 waiter/anchor/abort state，资源有界；
4. **Observability/performance:** trace 完整、低扰动、可诊断。

bug 定级看其违反的最高层；是否进入核心模型则看最小可观测 obligation，而不是只有“是否已找到 isolation anomaly”一个布尔条件。

## 4. 执行范围与停止条件

### In Scope

- 五个 acquire 方法的 txWaitMap outer cleanup；
- wait-loop requestSet cleanup，尤其 interrupt；
- reentrant、normal grant、timeout、interrupt、deadlock abort 五类退出；
- S/X/IS/IX/SIX 五模式；
- pristine、cleanup-fixed 两变体差分；
- Serializable、Repeatable Read、Read Committed 的 bounded A/B histories；
- 独立 wait-lifecycle model、generated exit schedules 与 quiescent probe oracle；
- 受影响 mapping、源码链接、自动化和新证据。

### Out of Scope

- 同时合入 PR #95 的 lockerMap ConcurrentHashMap 改动；
- 重写 age-based deadlock policy；
- 声称已证明三个 isolation level；
- 将完整 Java notifier queue、真实时间或所有 SQL/B-tree 路径并入 micro-model；
- 覆盖或改写 Week 1–3 历史结果。

### Stop Conditions

- 若最小 cleanup fix 改变 owner compatibility 或 grant/release trace，停止并分类为 semantic regression；
- 若 A/B 出现 isolation history 差异，先保存最小见证并升级为 safety investigation，不继续泛化模型；
- 若 2 tx × 2 resource micro-model 超过 100,000 distinct states 或 60 秒，先做 symmetry/phase abstraction，不删 cleanup exit；
- 若必须增加生产 trace event，先单独评估 schema compatibility 与 low-sink 开销，不把它混入 cleanup 修复提交。

## 8. 风险与评审决策点

- **并发同事务调用：** value-conditional remove 只能避免不同 anchor 覆盖；相同 tx/same anchor 并发仍需要 unique token。实施前确认 transaction thread-affinity contract，并决定测试还是支持。
- **PR #95 范围：** 本计划只修等待清理，不顺带修改 lockerMap；existing two-witness matrix 的预期会从 2 pristine failures 变成 cleanup-fixed 仍有 1 unrelated failure，automation 必须按变体解释。
- **trace schema：** 首版使用 test-only quiescent probe；只有跨系统迁移确实需要 production event 时，才另开 schema/overhead 计划。
- **isolation claim：** 即使三 manager A/B histories 相同，也只能降低直接 safety 风险置信度，不能消除 liveness、resource-bound 或未覆盖路径风险。
- **模型分层：** micro-model 是 L3 前置组件；不得因它通过就宣称完整 age-based abort/timeout/recovery L3 已验证。
